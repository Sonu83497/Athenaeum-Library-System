# Database Design

MySQL 8+. See `database/schema.sql` for the raw DDL (mirrors
`backend/app/models`) and `database/seed.sql` / `backend/app/utils/seed.py`
for demo data.

## Entity overview

- **users** — login identity (email/password/role). One row per person who
  can log in, regardless of role.
- **members** — 1:1 extension of `users` for library-membership fields
  (membership ID, status, join date). Only member-role users have a row
  here today, but the design allows staff to also hold a membership if
  needed later.
- **authors**, **categories** — lookup tables, many-to-many with `books`
  via `book_authors` / `book_categories`.
- **books** — catalog entry with `total_copies`/`available_copies` kept in
  sync by the borrowing service on issue/return.
- **book_copies** — individual physical copy tracking (copy code,
  availability), for libraries that want to track specific copies rather
  than just a count.
- **borrow_transactions** — one row per issue; `status` moves
  `active -> returned` or `active -> overdue -> returned`. `due_date` and
  `status` are indexed since they're the most common report/AI-tool filter.
- **fines** — 1:1 with a `borrow_transactions` row, created only when a
  return is late. `amount = overdue_days * DAILY_FINE_AMOUNT` (configurable
  via env, see `app/services/fine_rules.py`).
- **feedback** — member ratings/comments, with a staff review flag.
- **notifications** — per-member notification feed, generated by the
  borrowing/fine services on issue, return, overdue, and fine events.
- **audit_logs** — who did what (issue/return actions today), for
  accountability.

## Relationships

```
users 1───1 members
members 1───* borrow_transactions
members 1───* fines
members 1───* feedback
members 1───* notifications
books  *───* authors      (via book_authors)
books  *───* categories   (via book_categories)
books  1───* book_copies
books  1───* borrow_transactions
borrow_transactions 1───1 fines
```

## Indexes

Applied on the columns queried most often: `users.email`,
`members.membership_id`, `books.isbn`, `books.title`,
`books.publication_year`, `borrow_transactions.member_id`,
`borrow_transactions.book_id`, `borrow_transactions.status`,
`borrow_transactions.due_date`, `fines.member_id`, `fines.status`,
`notifications.member_id`, `audit_logs.created_at`.

## Business rules enforced at the service layer (not just DB constraints)

- A member cannot borrow a book with `available_copies == 0`.
- A member cannot hold two simultaneous active loans of the same book.
- A member cannot exceed `MAX_BOOKS_PER_MEMBER` (env-configurable, default 5)
  active loans.
- Returning an already-returned transaction is rejected.
- `available_copies` is only ever mutated by `issue_book`/`return_book` in
  `app/services/borrow_service.py`, inside the same DB transaction as the
  `borrow_transactions` row, so the two never drift out of sync.

## Migrations

Alembic is configured in `backend/alembic/` and reads `DATABASE_URL` from
the same `.env` as the app (see `backend/alembic/env.py`). Generate the
first migration once your MySQL instance is available:

```bash
cd backend
alembic revision --autogenerate -m "initial schema"
alembic upgrade head
```

For quick local/demo use without MySQL, the app also auto-creates tables on
startup when `DATABASE_URL` is SQLite (see `app/main.py`) — Alembic is
still the source of truth for MySQL/production.
